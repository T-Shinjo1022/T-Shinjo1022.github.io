## 最初にお願いすること
1. リポジトリの構成、使用技術、共通部品、既存ページを確認する。
2. 既存のデザイン・コーディング規則を説明する。
3. **`docs/common/ファイル構成と命名規則.md` と照合して、変更するファイルの正確なパス・ファイル名・変更理由を一覧で提示する。**
4. 不明な事実や仕様は質問する。いきなり大規模変更をしない。
5. **実装に入る前に、提示したレイアウト・キャッチコピー・変更ファイルについて私の確認を取る。**

## ファイル構成・ファイル名の厳守
- **新規作成するHTML・CSS・JavaScript・画像は、必ず `docs/common/ファイル構成と命名規則.md` で指定された場所とファイル名にする。**
- **ページ名、ファイル名、フォルダ名をAIの判断で変更しない。** 例：`seminar/vr.html` を `vr-seminar.html` に変更しない。
- HTMLはページごとに分ける。ゼミページは `seminar/` に配置する。
- CSSは共通の `css/common.css` とページ専用CSSに分ける。ゼミページは `css/seminar.css` も使用する。
- JavaScriptは共通の `js/common.js` を利用し、ページ専用JSは必要な場合だけ追加する。追加前に相談する。
- 画像はページごとの `images/` 配下に置く。ゼミ画像は `images/seminar/ゼミ名/` に置く。
- 新しいWeb公開用ファイル名・フォルダ名は原則として**英小文字・数字・ハイフン**で命名する。既存の日本語名の設計資料は変更しない。
- **担当範囲外のファイルは作成・編集・移動・削除しない。** 変更が必要なら理由を説明し、事前に許可を取る。
- まだ存在しない共通ファイルを勝手に独自仕様で作成しない。Aに確認する。

## 実装条件
- 既存の技術構成（HTML / CSS / JavaScript）を維持する。新規フレームワークや外部ライブラリを無断導入しない。
- 共通ヘッダー・フッター・共通CSS/JSはAが担当するため、勝手に作り直さない。
- `css/common.css`、`js/common.js`、`css/seminar.css`（ゼミ共通）、`docs/design-guide.md` の変更はAへ事前相談する。
- 担当範囲を超える変更が必要なら事前に知らせる。
- 研究室・教員・学生・研究・設備・進路・業績・イベントに関する事実を創作しない。
- 未確認情報は `[要確認]` などで明示する。
- 文章・キャッチコピーは後から差し替えやすくする。
- PCとスマートフォンの表示に対応する。
- ゼミページでは他のゼミと共通の構成を使う。
- 画像に適切な `alt` を設定し、リンクのパスはHTMLの配置階層に応じて正しく指定する（例：`seminar/vr.html` から共通CSSへは `../css/common.css`）。

## 文章とデザイン
まずレイアウト案を簡潔に示し、キャッチコピーを3〜5案、各案の狙いとともに提案してください。採用する案を相談した後、コードを実装してください。文章は提供情報から作り、事実を追加しないでください。

**デザイン統一のための追加条件**
- `index.html`、`css/common.css`、`docs/design-guide.md` が存在する場合は先に確認し、採用済みのHOMEのデザインを基準にする。
- 色、フォント、余白、ボタン、カード、ヘッダー・フッターは共通仕様を優先する。
- ページ固有のCSSクラスには `vr-`、`design-`、`about-` などの接頭辞を付け、他ページに影響させない。
- 共通デザインが未実装・未確定なら独自に決めず、Aへ確認する。

## 実装後の説明
- **新規作成・変更したファイルの正確なパス、ファイル名、役割**
- **ファイル構成・命名規則に従っていることの確認**
- コードの重要部分の説明（初心者向け）
- 文章・画像・色・余白の変更場所
- 起動・テスト・表示確認の手順
- 未確認事項と残タスク
- PRに貼る変更概要
- **担当範囲外の変更がないか、`git status` 等で確認する手順**
